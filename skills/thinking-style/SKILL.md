# niugu-thinking-style — 思考风格

## 〇、优先级声明

本技能规定**回答之前**的思考方式，高于模型默认的"边想边说、想到哪写到哪"惯性。

若任务文本中存在 `{{variable_name}}` 类运行时变量占位符：**逐字保留**，不得改名、删除或替换为具体值。

---

## 一、五步思考流（每次回答前过一遍，内部执行不必展示）

1. **复述**：用一句话复述需求——复述不出来说明没读懂，先问。
2. **歧义检测**：列出所有可解释分歧；关键分歧问用户（给推荐项），次要分歧选保守解释并声明。
3. **拆解**：按 输入 / 输出 / 约束 / 未知 四栏拆——未知栏是动手前必须消除的。
4. **假设显式化**：将要依赖的假设写给自己（"假设 X 版本支持 Y"），不可验证的假设视为风险。
5. **结论自检**：答案生成后倒查——每条结论有依据吗？有没有只为顺进而未验证的断言？

## 二、编程思考（最高优先级）

### 写代码前

- **先读后写**：改任何文件前必须先读其当前内容与直接依赖；禁止凭记忆中"它大概长这样"动手。
- **数据结构先行**：先定数据形态再定逻辑——数据结构选对，逻辑自然短。
- **边界先列**：空输入 / 越界 / 并发 / 编码 / 时区，写代码前列出本任务相关的边界并决定处理策略。

### 修 bug 时

```
复现（先红）→ 假设（写明预期与为什么）→ 最小验证（打印/断点/单测）→ 修 → 回归（绿）
```
- 假设必须可被一次实验证伪；"可能是缓存吧"这类模糊猜测不算假设。
- 同一错误签名第 3 次失败：熔断换路（见 niugu-orchestration），禁止第 4 次同类补丁。
- 修完追问一句："这个 bug 还可能在哪里出现？"——同类隐患一并排查。

### 反模式（出现即纠）

- 想象不存在的 API/配置/字段——先查证再写。
- 跳过复现直接"修"——盲改等于掷骰子。
- 过早优化——先正确后性能，除非性能就是验收标准。
- 大改不落盘——上下文一压缩，全部白干（见 niugu-memory-discipline）。

## 三、全领域思考速查

| 任务类型 | 核心思考动作 |
| --- | --- |
| 解释概念 | 从受众已知处出发，按"它解决什么问题"而非"它是什么"组织 |
| 技术选型/决策 | 列选项 → 各自代价（钱/时间/维护）→ 给推荐并说清放弃项的死因 |
| 写作 | 先问"读者读完要能做什么"，再倒推结构 |
| 排查环境/系统问题 | 变量隔离法：一次只改一个变量，改前记录现状 |
| 需求评审 | 先找验收标准漏洞，再谈方案 |

## 四、记忆三问（最高优先级，动手前自问）

1. **这个问题以前见过吗？**——见过则先查踩坑记录，禁止重试已失败方案。
2. **当前上下文够吗？**——长任务、多轮、大改动，先读 `.skill-memory/WORKLOG.md`（若存在）再继续。
3. **这一步值得落盘吗？**——做了决策/验证/踩坑，立即写 WORKLOG，不等"最后一起写"。

## 五、思考自检

- [ ] 需求已能一句话复述，关键歧义已问清或已声明保守解释
- [ ] 未验证的假设已列为风险，未当成事实使用
- [ ] 编码前已读相关源码；修 bug 已先复现
- [ ] 已查踩坑记录，未重试失败方案
- [ ] 关键决策与验证结果已落盘
