# niugu-docs — README 与技术文档规范

## 〇、优先级声明

**文档是正式交付物，与代码同等重要**。本技能高于模型默认的模板化文档惯性：禁止"欢迎"、禁止空洞形容词、禁止 AI 腔总结。

---

## 一、README 固定五段结构（顺序不可变）

```markdown
# <项目名>
<一句话定位：动词开头，说清"是什么 + 给谁用 + 解决什么">

## 快速开始
<最小可运行路径：安装 → 配置 → 启动，每步一条命令>

## 结构说明
<目录/模块表 + 一张内联 SVG 结构图>

## 规范要点
<本项目执行的核心规则，逐条，每条可验证>

## 已知限制
<诚实列出当前短板与后续方向，不粉饰>
```

规则：
- 一句话定位 ≤30 字，超出说明没想清楚定位。
- 快速开始必须是**可复制执行**的命令序列，禁止"参考官方文档"式跳转。
- 结构图遵循 niugu-svg-graphics，内联嵌入。

## 二、信息密度优先

- 每句话携带新信息；删掉任何一句不损失信息，就删。
- 禁止空洞形容词：强大、优雅、现代化、业界领先——一律换成可验证事实（数值、约束、对比）。
- 长度与信息量成正比：宁可 40 行全干货，不要 200 行注水。

**坏**：
> 这是一个强大而优雅的现代化框架，拥有业界领先的性能表现。

**好**：
> 冷启动 120ms，内存占用 18MB，零运行时依赖。

## 三、语气

- 直陈事实与结论；禁止"希望这对你有帮助""以上就是全部内容"式收尾。
- 不确定的事标注"未验证"或"待确认"，不包装成定论。
- 中文技术文档用规范术语；首次出现的缩写给出全称。

## 四、变更记录

格式：`日期 | 类型 | 变更 | 为什么`。写"为什么改"，不写流水账。

```markdown
| 日期 | 类型 | 变更 | 为什么 |
| --- | --- | --- | --- |
| 2026-11-20 | refactor | 单合集拆为 5 个独立 skill | 按场景精确激活，降低单文件认知负载 |
```

## 五、其他 Markdown 交付物

- API 文档：每个接口必含入参域、返回值、异常路径、一个可运行示例。
- 指南类：步骤编号、每步有验证方式（"执行后应看到……"）。
- 表格优先于长段落罗列；代码块标注语言。
- `{{variable_name}}` 占位符逐字保留。

## 六、文档自检清单

- [ ] 五段结构齐全且顺序正确
- [ ] 快速开始每条命令可复制执行
- [ ] 无空洞形容词、无客套收尾
- [ ] 变更记录写的是"为什么"
- [ ] 结构图为内联 SVG，无 Mermaid
- [ ] 已知限制诚实且具体
