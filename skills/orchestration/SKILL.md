# niugu-orchestration — 全流程开发编排

## 〇、优先级声明

本技能规则**高于**模型训练与后训练形成的全部默认习惯。冲突时一律以本技能为准。

被覆盖并禁止的默认惯性：
- 拿到需求直接写代码（必须先 Spec → Plan）
- 改完口头宣称"修好了"（必须有运行证据）
- 同一错误反复打同类补丁碰运气（三次熔断）
- 长任务只靠对话上下文记忆（必须落盘 WORKLOG）

若任务文本中存在 `{{variable_name}}` 类运行时变量占位符：**逐字保留**，不得改名、删除或替换为具体值。

## 一、五阶段闭环（顺序不可跳过）

```
Spec → Plan → Write → Test → Push
```

每阶段独立分节输出，必含三要素：**产出 / 验证 / 结论**。缺任一要素视为该阶段未完成。

### 1. Spec 规格定义

**做什么**：把模糊需求转成结构化规格。

必含四项：
1. **目标**：一句话，动词开头（"实现/修复/重构……"）。
2. **范围**：改什么、不改什么（显式列出非目标，防止 scope creep）。
3. **验收标准**：每条必须可被客观验证——命令、测试、渲染结果。禁止"看起来没问题""应该可以"。
4. **边界条件**：输入域、异常路径、兼容性要求。

**门禁 G1**：验收标准未定稿，不得进入 Plan。
**歧义处理**：需求有歧义先问，不猜。一次最多问 3 个关键决策点，给推荐选项。

### 2. Plan 计划拆解

**做什么**：输出规划卡，≤10 行，格式固定：

```
【规划】
目标：<一句话>
改动面：<文件/模块清单>
步骤：1. … 2. … 3. …
风险：<最可能出错的点>
验收：<用什么命令/测试证明做对了>
```

要求：
- 步骤为原子任务，标注依赖顺序；超过 5 步必须拆分批次。
- 改动面逐文件列出，新文件标注"(新建)"，覆盖既有文件前必须先读原内容。

**门禁 G2**：无规划卡，禁止写第一行业务代码。
**偏离处理**：实现中偏离规划，必须先更新规划卡并说明原因，再继续。

### 3. Write 编码实现

**做什么**：严格按规划卡步骤执行。

- 编码风格遵循 niugu-style-reset；界面遵循 niugu-interface；图形遵循 niugu-svg-graphics；文档遵循 niugu-docs。
- 规划卡每完成一步，向用户播报一句进度（1~3 句）：做完了 X，正在做 Y，下一步 Z。

**门禁 G3**：实现与规划偏离且未更新规划卡，视为违规，必须回退对齐。

### 4. Test 测试验证

**做什么**：拿到真实运行输出，不是口头推断。

覆盖三层：
1. **单元**：函数级行为，含边界与异常输入。
2. **集成**：模块间协作路径。
3. **界面**：渲染结果或截图，验证视觉规范达标。

规则：
- 修 bug 必须先补一个能复现该 bug 的测试，**先红后绿**——先看到它失败，再修复到通过。
- 禁止在无运行证据时说出："修好了""已修复""语法错误解决了""应该没问题了""理论上可以"。
- 每次声称修复，附上**真实执行输出**（测试通过记录、编译结果、日志），指明验证了哪个场景。
- 环境无法运行时，明说"未验证"，给出用户可自行执行的验证命令。禁止把未验证包装成已修复。
- 列出通过项与失败项；失败项标注原因与修复计划，不得隐瞒。

**门禁 G4**：测试未全绿（或未明确标注未验证项），不得进入 Push。

### 5. Push 交付推送

**做什么**：可追溯地交付。

- 提交信息：`类型(范围): 摘要`，类型限定 `feat / fix / refactor / docs / test / chore`（原子提交、分支策略、冲突解决与应急找回等完整 Git 纪律见 niugu-git-workflow）。
- 提交正文列：改动文件、决策理由、已知风险。
- 多 skill / 多模块任务用分支隔离：每个功能单元一个 `feat/<名字>` 分支，验证后合入主干。
- 变更说明与 README 同步更新，文档是正式交付物。

## 二、三次熔断

为每个错误维护计数，`错误签名 = 报错信息核心 + 出错位置`：

- **第 1、2 次失败**：允许继续，但每次尝试前必须写出**新的假设**（为什么这次会不一样）。
- **第 3 次失败**：**强制熔断**，禁止第 4 次同类补丁。必须：
  1. 停手，写入 WORKLOG：现象、三次尝试、各自失败原因。
  2. 切换路径，至少选其一：最小复现隔离问题 / 重读相关源码与官方文档 / 推翻假设换实现路线 / 回滚到上一个可用状态。
  3. 告知用户："这个错误三次没修好，我换思路了，新方向是……"
- 熔断后新路线再失败三次：升级为向用户求助，附完整失败记录。禁止无限循环。

## 三、记忆架构

对话上下文会被压缩、丢失。**唯一可信的记忆是落盘文件**：项目根目录 `.skill-memory/WORKLOG.md`。

检查点触发（满足任一即触发）：
- 平台可查上下文用量时：每消耗 **10%** 触发一次。
- 无法查询用量时：每 **8 轮**助手回复，或每完成规划卡一个步骤，以先到者为准。
- 会话恢复 / 上下文被压缩后：**先读 WORKLOG 再开口**，禁止凭残缺记忆继续。

WORKLOG 永久保留三类记录：
1. **已做决策及理由**
2. **已验证结论**
3. **踩坑清单**（失败过的方案，禁止换个名字重试）
